# Bugs Found and Fixed — Testbed-T1.0.0 Starter Code

**Summary:** 13 bugs found and fixed in the starter code (Part A). The four with the biggest effect:
the build failing (#1), the lidar seeing only 1.5 m (#6), `base_footprint` off the rotation centre (#12),
and the brick walls jumping 1.25 m on Reset World (#13). With all fixes, the robot reaches 5 of 5 goals
on a 57 m tour with 0 recoveries (see `testbed_navigation/README.md`). Part B logs the 11 issues I hit
while building the `testbed_navigation` package, and how I solved each one.

**Environment:** Ubuntu 22.04, ROS 2 Humble, Gazebo Classic 11.10.2

**Status legend:** ✅ Fixed and verified  ·  🔍 Waiting on something outside the project  ·  ➖ Deliberately not fixed

**How bugs were verified:** a build check (`colcon build`), a URDF parse (`xacro` + `check_urdf`), dependency checks (`rosdep check`), and simulation tests (`testbed_navigation/scripts/`). In this simulation `/odom` is the robot's true pose (the diff-drive plugin's default world odometry, checked against Gazebo's own model pose), and the map frame is the world frame, so commanded vs actual motion and AMCL's exact localization error can both be measured.

### Checked and found OK (not bugs)
- **Wheel/caster friction** (all μ = 0.2) looked suspicious, because the four casters are fixed links that slide rather than roll. The drive test showed no slip, though: commanding 0.2 m/s for 5 s moved the robot exactly 1.00 m forwards and 1.00 m backwards. Left unchanged.
- `wheel_diameter = 0.1`: the wheel mesh spans z = 0.0 → 0.1 m.
- The lidar sits above the body (lidar z ≈ 0.228 m, top of body ≈ 0.2225 m), so it doesn't see the robot itself.
- The map frame matches the Gazebo world frame: the map covers x −10.2 → 10.05 m and y −9.94 → 10.06 m. The robot spawns at **(0, 5, yaw 0)**, which becomes AMCL's initial pose.
- `testbed.trans` uses ROS 1 transmissions. It isn't used in ROS 2 but does no harm, so I left it unchanged.
